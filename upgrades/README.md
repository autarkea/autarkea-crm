# 📦 Каталог миграций-дельт (upgrades/)

Дельты — это **аддитивные** изменения схемы установленной у клиента CRM:
новые колонки, таблицы, опции селектов, связи. Они применяются движком
`upgrade.sh` поверх живой базы **без потери данных клиента**.

## Правила (не нарушать)

1. **Только аддитивность.** Дельта добавляет недостающее и никогда не удаляет
   существующее (колонки, данные, чужие правки клиента).
2. **Идемпотентность.** Повторный запуск дельты безопасен: если колонка/опция
   уже есть — дельта просто пропускает шаг. Ядро `modules/*.sh` уже так работает.
   ⚠️ Идемпотентность по ИМЕНИ безопасна только для АДДИТИВНЫХ правок. Если смысл
   поля меняется (список → одиночная связь, текстовое → вложение), дельта обязана
   сама различить состояния и мигрировать данные — иначе шаг «уже есть» пропустится
   молча. Пример: `U017_kontakt-otvetstvennyy.sh` (Проблема 134).
3. **Запускай модули последовательно.** `SKIP_RESTART=1 bash modules/add-column.sh …`
   и `SKIP_RESTART=1 bash modules/add-link-m2o.sh …` — перезапуск делает движок
   `upgrade.sh` (шаг 7). Параллельный запуск двух модулей на одной базе даёт
   `database is locked (5)`.
4. **Нумерация.** Имя файла: `U<NNN>_<короткое_имя>.sh`, номер строго растёт.
   Движок применяет только дельты с номером больше текущей версии схемы.
5. **Одна дельта = одна фича.** Не смешивать: «добавил колонку + поменял селект»
   лучше двумя дельтами, чем одной. Это упрощает откат и понимание.
6. **Автобэкап.** Каждая дельта должна полагаться на автобэкап `upgrade.sh`,
   но при прямом запуске (`bash upgrades/U001_...sh`) — делать свой бэкап.
7. **Версия.** В конце дельта **НЕ** пишет версию — это делает движок `upgrade.sh`
   (один источник правды). При прямом запуске — просто выполняется.
8. **Структура БД.** Прямые SQL — только через `modules/*.sh` или с теми же
   предохранителями (транзакция, `.bail on`, проверка существования).
9. **После дельты** — обновить `shared/columns.js` (`generate-columns-map.sh`),
   если появились новые колонки, и задокументировать изменение.
10. **Граница миграции: виды и раскладку UI НЕ мигрируем.** Дельты догоняют схему и
    СМЫСЛ (таблицы, колонки, типы, смысл связей, опции селектов), но не раскладку.
    Если сомневаешься — спроси себя: «фича физически не работает без этого вида?».
    Нет → клиент настроит сам (раздел «Что мигрируем дельтами, а что живёт только
    в эталоне» ниже).

## 🚨 Главное правило: правка в UI NocoDB ⇒ дельта в тот же день

Схема клиента обновляется ТОЛЬКО кодом и дельтами. `template.db` доставляет состав
**лишь на свежую установку** (`install.sh`/`apply-template.sh` — это пересоздание
базы), на апдейте он не применяется.

Поэтому: **если ты поправил схему руками в интерфейсе NocoDB — напиши дельту под
эту правку сразу**, ещё до экспорта шаблона. Иначе фича уедет в `template.db`
(эталон снимается с живой базы) и будет ждать там свежей установки, а у клиентов
её не будет вовсе. Так и случилось с «Фото» в «Контакты»/«Юрлица» и связью
«Контакт/ответственный» — Проблема 134, дельты `U016`/`U017`.

Порядок работ (проверен на v4.69.0 и v4.70.0):

```bash
# 1. дельта (по шаблону выше) — на живой базе она, как правило, «пропуск»
bash upgrades/U0NN_имя.sh
# 2. эталон: маркер версии (12.5) + слепок состава (12.6) + чистка (8.11)
bash export-template.sh
# 2.5. дрейф: что изменилось в эталоне и покрыто ли это дельтой (виды — «эталон-онли»)
bash modules/schema-drift.sh
# 3. карта колонок, если появились новые поля
bash modules/generate-columns-map.sh   # результат — в shared/columns.js
# 4. тесты + репетиция на копии базы
node --test tests/
bash upgrade.sh --db-only --db /tmp/client_copy.db
```

**Догон того, что уже разъехалось.** Состав эталона и состав живой базы сверяет
`modules/schema-fingerprint.sh check` (быстро, без данных клиента: только имена,
типы и смысл связей):

```bash
bash modules/schema-fingerprint.sh check      # 0 — состав как в эталоне, 1 — расхождение
bash modules/schema-fingerprint.sh check --quiet
```

Слепок состава пишется в `nc_store` (`printed4u_schema_fingerprint`) подшагом 12.6
экспортёра, сверяется в `upgrade.sh` (шаг 9, предупреждение — не ошибка) и
показывается в `diagnose.sh` (§12). Он ловит то, что по именам не видно: поле с тем
же названием, но другим СМЫСЛОМ (список `om` вместо одиночной `mo`).

## 🎯 Что мигрируем дельтами, а что живёт только в эталоне

Дельты догоняют **состав и смысл**, но не **раскладку**. Граница проходит по вопросу
«сломается ли фича, если у клиента этого нет?».

| Сущность | Класс | Почему так |
|---|---|---|
| Таблицы (`nc_models_v2`) | 🧩 мигрируем | без таблицы фича не работает |
| Колонки и тип (`uidt`: текст/число/вложение/связь) | 🧩 мигрируем | то же; тип входит в слепок, подмена ловится (пример — «Фото»: `Attachment`) |
| Смысл связи (`mo`/`om`/`hm`/`mm`) и подписи | 🧩 мигрируем | от смысла зависит поведение поля (Проблема 134: список вместо одиночной связи) |
| Опции селектов (названия и цвета) | 🧩 мигрируем | это значения бизнес-логики (статусы, роли, типы документов) |
| Виды (`nc_views_v2`): набор, тип, порядок/видимость колонок вида, `nc_filter_exp_v2`, `nc_sort_v2`, настройки kanban/календаря, подсветка строк | 🖼 **эталон-онли** | это рабочее место клиента: виды он создаёт, сортирует и удаляет сам. В поставку едет только тот вид, без которого фича ФИЗИЧЕСКИ не работает — и это должно быть сказано в шапке дельты |

**Пример (решение владельца, 15.09.2026):** вид **«Канбан» у таблицы «Проекты»** —
«эталон-онли». Он сделан для демо/скриншотов «причёсанной CRM», в клиентскую поставку
не едет. В `template.db` он есть — и это нормально (эталон показывает, как выглядит
разобранная CRM), но `upgrade.sh` его никому не навязывает и клиентские виды не откатывает.

**Как это проверяется:**

- `bash modules/schema-drift.sh` — что изменилось в эталоне относительно последнего
  коммита: 🧩 мигрируемое с покрытием (`✅ покрыто [U0NN]` / `⚠️ НЕТ ДЕЛЬТЫ`),
  🖼 виды как «эталон-онли», 🧹 исчезло. Встроен в экспортёр подшагом **12.7** — барьер
  стоит в момент причёсывания эталона, а не после релиза (`--strict` → код 1);
- инвариант ОТК в `tests/template-schema.test.js`: «правка в UI ⇒ дельта» — но
  только по СОСТАВУ (виды намеренно не проверяются) + «нет осиротевших настроек видов»;
- `modules/schema-fingerprint.sh` — слепок состава (таблицы/колонки/типы/смысл
  связей/опции). Виды в слепок НЕ входят: иначе у каждого клиента со своим видом было
  бы вечное расхождение;
- `modules/schema-compare.sh` — по видам печатает справочную строку «эталон N,
  у клиента M — расхождение НЕ ошибка».

## Шаблон дельты

```bash
#!/bin/bash
# upgrades/U001_имя-фичи.sh
# Что делает: ...
# Целевая версия: 1
set -euo pipefail

NOCO_DB="${NOCO_DB:-/mnt/data/nocodb-data/noco.db}"
cd "$(dirname "${BASH_SOURCE[0]}")/.."

echo "📦 U001: ..."

# Пример: добавить колонку (идемпотентно — add-column сам проверит)
bash modules/add-column.sh "Проекты" "Новая колонка" "TEXT" "Описание" || true

echo "✅ U001 завершена"
```

## Запуск

```bash
bash upgrade.sh                  # применить все недостающие дельты (безопасно)
bash upgrade.sh --dry-run        # показать план, ничего не менять
bash upgrades/U001_имя.sh        # одна дельта вручную (с автобэкапом modules)
```

> ⚠️ **«Большой скачок» (v4.46.0):** если клиент обновляется с очень старой версии,
> префлайт `upgrade.sh` сканирует `upgrades/` ДО `git pull` — новые дельты, которые
> приезжают вместе с кодом, в первый проход не попадают (симптом: «версия схемы не
> менялась» при уже обновлённом коде). С v4.46.0 `upgrade.sh` догоняет их шагом 5.5
> (реконсиляция) в том же запуске. Если апдейт уже был сделан старой версией
> скрипта — просто запусти `bash upgrade.sh` повторно: дельты идемпотентны,
> применятся недостающие и запишется актуальная версия схемы.

## 🧪 Проверка устойчивости к обрыву (U2)

Механизм «версия схемы пишется только в конце (шаг 9) + дельты идемпотентны»
проверяется автоматически на **копии БД** (живая база не трогается):

```bash
bash tests/upgrade-u2-e2e.sh        # обрыв на середине → повтор-«догон» (17 проверок)
```

Что делает тест: копирует `noco.db`, ставит маркер схемы на `U6`, ставит «гейт»
`U009` между U008 и U010, убивает `upgrade.sh` (SIGKILL), затем повторяет прогон —
и убеждается, что версия «догоняется» до `U10` **без дублей и потери данных**.

> Обычные прогоны движка для репетиций на копии: `upgrade.sh --db-only --db <copy>`
> (флаг `--db-only` включает `--skip-modules` — host-cron `health-alert`/`fix-fs`
> не трогается, `sudo` не нужен).
